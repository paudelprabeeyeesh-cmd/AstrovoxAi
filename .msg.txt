perf(astrovox): fix the two bottlenecks measurement actually found

Profiling a training step contradicted the earlier guess. The cost was not
graph construction or view materialization; it was an error function.

GELU computed erf through np.vectorize over a Python approximation, which
made 12,582,924 interpreter calls per forward pass. That single line was 70
percent of the forward and 60 percent of a whole training step. Replacing it
with array operations over the same Abramowitz and Stegun 7.1.26 polynomial
gives bit-comparable values and removed the interpreter entirely.

The approximation is evaluated in the input's own precision. Its error is
about 1.5e-7, which is the limit of float32, so promoting to float64 bought
nothing the dtype could hold while allocating a wide temporary per call.
Measured against a float64 reference, the float32 result is within 1e-7.

SciPy is used when installed, and the lookup is resolved once at import:
attempting the import inside the hot path made every GELU call re-run a
failing import, which cost real time on machines without SciPy.

A Linear weight is now stored so that its transpose is contiguous. The layer
computes x @ weight.T, and with a row-major weight that transpose is strided,
so NumPy copies the whole weight to hand it to BLAS on every forward call.
Storing the buffer transposed makes the hot path contiguous. The trade is a
strided write when an optimizer updates the weight, which is the right way
round because forward and backward dominate.

Fixing that surfaced a latent bug in Tensor._writable. It returned a
row-major reshape of the storage, which is wrong for any strided tensor: an
in-place update would be written to the wrong memory positions. It now
returns a strided alias, so the layout is honoured. A weight is a leaf that is
an optimizer writes every step, so this surfaced as a model that would not
train at all rather than as a subtle numerical drift.

Measured on a 3.0M-parameter transformer, batch 8 by 64:
  before  1060 ms/step, 2.99 GFLOP/s
  after    873 ms/step, 3.63 GFLOP/s
The forward pass alone went from 3702 ms to about 620 ms, a factor of six,
which is the erf change alone.

223 tests pass. The transformer still trains: validation loss 2.99 to 2.74.
